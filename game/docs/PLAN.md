# PLAN — 단계별 구현 계획과 완료 기준

> 영상의 핵심 원칙대로, 각 단계는 **완료 기준을 모두 만족해야** 다음 단계로 넘어갑니다.
> ✅ = 이번 커밋에서 완료·검증 / ⬜ = 예정

## Phase 0 — 기획 ✅
- 산출물: `docs/ANALYSIS.md`, `docs/PRD.md`, `docs/PLAN.md`
- 완료 기준
  - [x] PRD에 핵심 루프, 규칙, **숫자로 된 밸런스 목표**가 있다
  - [x] 단계마다 완료 기준이 있다

## Phase 1 — 화면 없는 규칙 엔진 ✅
- 산출물: `src/types.ts`, `src/engine.ts`, `src/data.ts`, `src/rng.ts`, `data/*.json`
- 완료 기준
  - [x] 모든 수치가 `data/*.json`에 있고 코드에는 없다
  - [x] 데이터 로드 시 참조 무결성 검사(없는 몬스터·던전 참조, id 중복, 기본 장비 누락)
  - [x] `step()`은 원본 상태를 바꾸지 않는다(불변)
  - [x] 시드가 같으면 같은 판이 나온다
  - [x] 문항 판정기(`Resolver`)로 실제 문항 풀이를 끼울 수 있다
  - [x] `tsc` 타입 검사 통과, 단위 테스트 13개 통과

## Phase 2 — 봇 밸런스 시뮬레이터 ✅
- 산출물: `src/bots.ts`, `src/sim.ts`, `data/targets.json`
- 완료 기준
  - [x] 봇 3종(잘함 / 열심히 / 대충)이 엔진 공개 함수만으로 플레이한다
  - [x] 봇 3종 × 300판이 2초 안에 끝난다(실측 약 1초)
  - [x] 목표 12개 모두 통과(시드 1~4 모두)
  - [x] `npm test`에 밸런스 회귀 테스트 포함(목표 이탈 시 실패)

## Phase 3 — 문항 연동 ⬜
- 할 일: `data/questions/*.json`(과목·단원·난이도·정답·해설) 형식 정의 → 등급별 난이도와 매칭 → `Resolver` 구현
- 완료 기준
  - [ ] 과목별 등급마다 최소 30문항(4과목 × 4등급 × 30 = 480문항)
  - [ ] 같은 날 같은 문항이 다시 나오지 않는다
  - [ ] 문항 데이터 검증: 정답 번호 범위, 선지 5개, 해설 존재
  - [ ] 오답 로그가 학생 ID 기준으로 쌓인다
- 참고: 이 저장소의 docread(시험지 판독)로 만든 정리본 `.docx`를 변형 문항의 원재료로 쓸 수 있습니다.

## Phase 4 — 화면(웹 2D 우선) ⬜
- 할 일: Vite + 2D(또는 Three.js) 마을 화면, NPC 대화, 상점, 전투 연출
- 완료 기준
  - [ ] 엔진 코드를 한 줄도 고치지 않고 화면을 붙인다(엔진은 import만)
  - [ ] 모바일 세로 화면(360px)에서 하루 행동 하나를 3탭 이내로 끝낸다
  - [ ] 대사는 `data/dialogue/*.json`에서 읽는다
- 권장: 3D는 볼거리를 만들지만 학습 효과와는 무관합니다. 재원생용이라면 2D로 먼저 출시해 문항 루프를 검증하는 쪽이 비용 대비 효과가 큽니다.

## Phase 5 — 계정·저장 ⬜
- 할 일: Supabase 인증, 세이브 테이블(학원 내부 ID, 상태 JSON, 버전), 기기 간 충돌 방지(버전 비교)
- 완료 기준
  - [ ] 옛날 버전으로 덮어쓰는 시도는 거부된다(낙관적 잠금)
  - [ ] 이름·연락처는 세이브 테이블에 없다
  - [ ] 원장용 학습 로그 조회(학생별 과목 숙련도 추이, 오답 단원 TOP 5)

## Phase 6 — 원내 베타 ⬜
- 완료 기준
  - [ ] 학생 5~10명이 2주간 사용
  - [ ] **사람 검증**: 봇이 통과시킨 수치가 실제로 재미있는지 설문(영상도 강조한 마지막 단계)
  - [ ] 실제 플레이 로그로 봇의 정답률 가정(잘함 1.0 / 열심히 0.9 / 대충 0.75)을 다시 맞춘다
