# 영상 분석: 「AI 코딩으로 하루 만에 3D RPG」의 방법론

- 대상: YouTube `_3JR1CKHdsg`. 원장님이 붙여 주신 자막(약 23분)을 기준으로 분석했습니다. 클라우드 세션에서 YouTube 접속이 차단되어 있어서 영상 페이지의 메타데이터(제목·채널·업로드일)는 확인하지 못했습니다.
- 자막은 음성 인식으로 만든 것이라 오탈자가 많습니다. 예: "오프스 5.5" = Opus 5.5, "곰치는" = 공치는, "레고 싶더" = 레거시 코더.

---

## 0. 결론 요약

1. **AI는 '만드는 일', 사람은 '정하는 일'을 맡았습니다.** 하루 만에 끝난 이유는 프롬프트 실력보다 **작업 구조**(PRD → 완료 기준이 있는 단계별 PLAN → 화면 없는 규칙 엔진 → 봇 밸런스 테스트 → 정돈된 기존 코드에 연결)에 있었습니다.
2. **경쟁 영상과 갈리는 지점은 '봇 밸런스 테스트'입니다.** 영상 스스로도 "다른 AI 게임 제작 영상에서 잘 안 보이는 장면"이라고 말합니다. 육성 RPG는 결국 숫자 싸움이고, 수백 판을 30초 안에 돌려 목표 11개를 통과시켰습니다.
3. **"하루"는 그대로 믿으면 안 됩니다.** 실제로는 약 1.5일, 20시간 이상이 걸렸습니다. 제작자에게는 10여 년 전 RPG 개발 경험, 이미 잘 정리된 웹사이트, 유료 이미지 API라는 세 가지 전제가 있었습니다.

## 2. 재사용 가능한 다섯 가지 장치

### ① PRD → PLAN → 단계마다 완료 기준
- PRD는 거창할 필요가 없습니다. 제작자도 "기억을 더듬어 대충 적었다"고 말합니다.
- 핵심은 PLAN의 각 단계에 **끝났는지 판단할 기준**이 있다는 점입니다. 이 기준이 없으면 AI는 "다 했습니다"라고 말하고 멈추거나, 반대로 범위를 끝없이 넓힙니다.
- 영상의 마지막 메시지도 이것입니다. 검증 기준을 높게 세우고 AI가 그 기준을 지키게 해야 합니다.

### ② 데이터와 코드 분리
- 대사, 능력치, 가격, 몬스터를 JSON 같은 데이터 파일에 둡니다.
- 효과: 밸런스를 조정할 때 코드를 고치지 않으므로 회귀 버그가 생기지 않습니다. 비개발자(원장님, 조교)도 수치와 대사를 고칠 수 있습니다.

### ③ 화면 없는 규칙 엔진 + 봇 시뮬레이션 (가장 중요)
- 2일차에 **화면보다 먼저** 만든 것이 터미널에서 돌아가는 게임 규칙이었습니다.
- 봇 3종(열심히 / 잘함 / 대충)이 1일차부터 마지막 보스까지 수백 판을 30초 안에 플레이합니다.
- 사람은 목표만 정했습니다("5~8시간, 초반엔 덜 죽고 중반에 벽").
- 결과: 상점에 살 게 없는 날이 66% → 29%로 줄었고, 목표 11개를 모두 통과했습니다.
- 한계(영상도 인정): 이 테스트는 숫자를 맞출 뿐 **재미를 보장하지 않습니다.** 마지막 검증은 사람이 해야 합니다.

### ④ AI에게 도구를 쥐여 주기
- 이미지 API를 Claude Code에 연결하자 프롬프트 작성 → 여러 장 생성 → 선택 → 적용이 한 흐름이 됐습니다.
- 몬스터 일러스트는 2단계로 만들었습니다. 먼저 AI가 3D 몬스터를 만들고, 그 모델을 참고해 이미지 AI가 그렸습니다. 그래서 게임 속 모습과 그림이 따로 놀지 않습니다.
- 제작자의 표현: "AI에게 적절한 도구를 적절한 순간에 쥐여 주는 것, 그게 엔지니어링."

### ⑤ 정돈된 기반 코드
- 로그인, DB, 클라우드 저장을 붙이는 데 13분이 걸렸습니다. 기존 웹사이트 구조가 깔끔했기 때문입니다.
- 제작자의 비유: 배선이 도면대로 깔린 집은 주방 리모델링이 금방 끝납니다.
- 같은 맥락에서 "AI는 주변 코드를 베낀다. 주변 코드가 잘 돼 있으면 잘 베낀다."

## 3. 사람이 결정한 것 vs AI가 한 것

| 사람(욕망·취향·판단) | AI(구현) |
|---|---|
| 무슨 게임인지, 누구를 위한 것인지 (바이브 코더 → 에이전틱 코더 성장 서사) | 모든 코드, 3D 모델, 애니메이션 |
| 세계관 장치: 던전 이름, 프로그래밍 언어 속성, 레거시 코더 라이벌, 패배 시 '롤백' | 몬스터 3D 모델, 이름 대부분 |
| "턴제는 지루하다" 같은 직접 플레이 판단 | 실시간 전투 40분 구현 |
| 이동속도, 맵 크기, 로고 7개 중 선택 | 시안 생성 |
| 밸런스 **목표** | 밸런스 **튜닝** |

제작자의 결론: "구현은 AI가 하고, 방향·결정·취향은 사람의 몫."

## 4. 팩트체크와 걸러 들을 점

| 주장 | 판정 | 근거·메모 |
|---|---|---|
| "하루 만에" | **과장** | 1일차 점심부터 밤 12시 반, 2일차 밤까지 작업했고 이후 폴리싱이 이어졌습니다. 실제 순작업은 약 20시간 이상으로 추정됩니다(자막의 시각 언급 기준). |
| 클라우드 저장 13분 | 맞음, 단 **조건부** | 기존 웹사이트(인증·DB)가 이미 있었습니다. 이것 없이 처음부터 만들면 가장 오래 걸리는 구간입니다. |
| 봇 테스트 30초, 목표 11개 통과 | 맞음, 단 **검증 불가** | 목표 정의를 공개하지 않았습니다. 이 저장소의 실증 예제로 같은 방식이 재현되는지 확인했습니다(아래 5장). |
| 몬테카를로 = 알파고 알고리즘 | 대체로 맞음 | 알파고는 몬테카를로 트리 탐색(MCTS)에 신경망을 결합했습니다. 몬테카를로 기법 자체는 그보다 훨씬 오래됐습니다. |
| 순보(瞬歩) = 블리치 | 맞음 | 블리치에 나오는 고속 이동 기술입니다. |
| "정식 게임 심의 전 클로즈 베타" | **리스크** | 국내에서 일반에 게임을 제공하려면 원칙적으로 게임물관리위원회 등급분류가 필요합니다(게임산업진흥법). 교육용 예외는 위원회 기준을 충족해야 합니다. |

영상은 제작자의 책, 무료 소스(웹사이트 기본 구조), 웹사이트 유입으로 이어지는 **마케팅 구조**를 갖고 있습니다. 게임 자체보다 "AI로 이 정도까지 만든다"는 시연과 채널 성장이 목적입니다.

## 5. 실증: 이 저장소에서 같은 방법론을 그대로 돌려 본 결과

영상 속 게임을 복제하지 않고, **오리지널 사탐 학습 육성 게임 「개념마을」**에 ①②③을 적용했습니다. 코드는 `game/`에 있습니다.

| 단계 | 결과 |
|---|---|
| 첫 시뮬레이션 | 목표 12개 중 **6개 통과** |
| 튜닝 반복(약 10회) | 목표 **12개 모두 통과**. 서로 다른 시드 4개 × 봇 3종 × 300판 = 3,600판, 약 1초 |
| 회귀 테스트 | `npm test`가 매번 150판씩 돌려 목표 이탈을 자동으로 잡아냄 |

튜닝 과정에서 **사람이 직접 플레이해서는 찾기 어려운 문제 4가지**가 드러났습니다.

1. **지표 정의가 거꾸로 되어 있었습니다.** 처음에는 '살 것 없는 날'을 "돈이 없어서 못 사는 날"로 정의했습니다. 영상이 말한 지표는 "돈은 있는데 쓸 데가 없는 날"입니다. 지표 하나를 잘못 정의하면 튜닝 방향이 정반대가 됩니다. **목표를 정의하는 일은 사람의 몫**이라는 점을 그대로 보여 줍니다.
2. **이해력→HP 연동이 너무 강했습니다.** 이해력이 1,000을 넘으면서 HP가 과도해지고 전투 긴장감이 사라졌습니다. 계수를 조정했습니다.
3. **전투 무작위 폭 ±15%가 실제로는 ±35%로 증폭되고 있었습니다.** 주는 피해와 받는 피해에 무작위가 곱으로 겹쳤기 때문입니다. 그래서 '이길 것'이라고 예측한 판의 약 30%를 졌습니다. 8%로 낮췄습니다.
4. **예상하지 못한 교육적 결과가 나왔습니다.** 다음 던전 과목만 공부하는 '잘하는 봇'은 과목이 섞인 모의고사에서 자주 졌습니다. 반대로 가장 약한 과목부터 고르게 공부하는 '열심히 하는 봇'은 거의 지지 않았습니다. 즉 이 규칙은 "편식하면 모의고사에서 진다"를 **강제하지 않아도 자연스럽게 학습시킵니다.** 학습 게임 설계에서 바로 쓸 수 있는 발견입니다.

남아 있는 문제는 `game/docs/PLAN.md`의 '남은 이슈'에 정리했습니다.
